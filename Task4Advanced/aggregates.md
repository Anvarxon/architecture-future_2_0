# Агрегаты: границы, инварианты, ключи

Для каждого агрегата указаны: **ключ** (идентичность), **границы транзакции**,
**инварианты** (правила, которые агрегат обязан удерживать всегда) и **публикуемые события**.

Общее правило: одна транзакция изменяет **один** агрегат. Согласованность между
агрегатами — событийная (eventual). Ссылки между агрегатами — только по идентификатору,
не по объекту.

---

## Контекст: Party & Identity

### `Party` — физическое или юридическое лицо

| | |
|---|---|
| **Ключ** | `party_id` (UUIDv7, генерируется доменом) |
| **Границы** | реквизиты лица, связи с другими Party, состояние (активна / объединена / заблокирована) |
| **Не входит** | роли в доменах (пациент, заёмщик, сотрудник) — это локальные понятия доменов |

**Инварианты**

* `party_id` неизменен на протяжении жизни; переиспользование запрещено.
* Не может существовать двух активных Party с одинаковой парой (тип документа, номер документа).
* Объединённая Party (`merged`) не может участвовать в новых операциях: все ссылки
  перенаправляются на целевую.
* Изменение реквизитов не создаёт новую Party — создаётся новая версия внутри агрегата.

**События:** `PartyIdentified`, `PartyAttributesUpdated`, `PartyMerged`, `PartyBlocked`.

> **Почему это отдельный агрегат.** Сейчас клиент клиники и клиент банка — разные записи
> в разных частях DWH, связываемые вручную. Единый `party_id` — необходимое условие
> сквозной отчётности и сценария «рассрочка на лечение».

## Контекст: Consent

### `ConsentGrant` — согласие на обработку данных

| | |
|---|---|
| **Ключ** | `consent_id`; бизнес-ключ — (`party_id`, `purpose`, `scope`) |
| **Границы** | цель обработки, состав данных, получатель, срок, состояние, история изменений |

**Инварианты**

* Согласие имеет ровно одно активное состояние: `granted`, `revoked` или `expired`.
* Отзыв необратим: возобновление — это новое согласие с новым `consent_id`.
* Обработка данных вне цели (`purpose`), указанной в согласии, невозможна.
* История изменений неизменяема (append-only) — требование доказуемости перед регулятором.

**События:** `ConsentGranted`, `ConsentRevoked`, `ConsentExpired`.

## Контекст: Patient Access

### `Appointment` — запись на приём

| | |
|---|---|
| **Ключ** | `appointment_id` |
| **Границы** | слот, пациент (`party_id`), врач, клиника, услуга, состояние |

**Инварианты**

* Один слот врача не может быть занят двумя активными записями (проверяется внутри
  агрегата `ProviderSchedule`, см. ниже).
* Переход состояний: `scheduled → (confirmed) → completed | cancelled | no_show`.
  Обратные переходы запрещены.
* Запись нельзя создать на прошедшее время и на врача без требуемой квалификации
  (квалификация приходит событиями из Workforce и кэшируется локально).

**События:** `AppointmentScheduled`, `AppointmentConfirmed`, `AppointmentCancelled`,
`NoShowRegistered`.

### `ProviderSchedule` — расписание врача

| | |
|---|---|
| **Ключ** | (`provider_id`, `date`) |
| **Границы** | слоты одного врача на один день — граница выбрана так, чтобы конкуренция за слоты решалась внутри одной транзакции |

**Инварианты**

* Слоты не пересекаются по времени.
* Суммарная длительность приёмов не превышает длительность смены (смена приходит из Workforce).
* Освобождение слота при отмене записи происходит в той же транзакции, что и изменение статуса слота.

**События:** `ScheduleSlotBlocked`, `ScheduleSlotReleased`, `SchedulePublished`.

## Контекст: Patient Care 🔒

### `Encounter` — клинический эпизод (приём)

| | |
|---|---|
| **Ключ** | `encounter_id` |
| **Границы** | факт приёма, участники, назначения в рамках приёма, состояние, ссылки на клинические записи |
| **Класс данных** | PHI — не покидает медицинский контур в исходном виде |

**Инварианты**

* Приём нельзя завершить, если есть незакрытые обязательные назначения.
* Клиническая запись после подписания врачом неизменяема; исправление оформляется
  дополнением со ссылкой на исходную запись (требование медицинского документооборота).
* Приём не может быть начат без действующего `ConsentGrant` на обработку медицинских данных.
* `encounter_id` связан ровно с одним `party_id` и одним `appointment_id` (либо создан
  как экстренный — без записи).

**События (в аналитический контур — без клинического содержания):**
`EncounterStarted`, `EncounterCompleted`, `EncounterCancelled`, `TreatmentPlanApproved`.

### `ClinicalOrder` — назначение (исследование, процедура)

| | |
|---|---|
| **Ключ** | `order_id` |
| **Границы** | тип назначения, исполнитель, состояние выполнения, результат (ссылка) |

**Инварианты**

* Назначение принадлежит ровно одному `encounter_id`.
* Отмена возможна только до перехода в статус «выполняется».
* Результат может быть присоединён только к назначению в статусе «выполняется» или «выполнено».

**События:** `ClinicalOrderPlaced`, `ClinicalOrderCancelled`, `ClinicalOrderFulfilled`.

## Контекст: AI Diagnostics 🔒

### `AIStudy` — анализ, выполненный моделью

| | |
|---|---|
| **Ключ** | `study_id` |
| **Границы** | запрос, версия модели, результат, уверенность, время выполнения, статус |

**Инварианты**

* Анализ не запускается без действующего согласия на обработку медицинских данных для цели «поддержка диагностики».
* Каждый результат жёстко связан с конкретной версией модели (`model_version_id`) —
  без этого невозможно расследование инцидента и аудит.
* Результат ИИ никогда не является диагнозом: агрегат хранит признак «требует
  подтверждения врачом» и не может его снять сам.
* Повторный запуск создаёт новый `study_id`; результаты не перезаписываются.

**События:** `AIStudyRequested`, `AIStudyCompleted`, `AIStudyRejected`, `AIStudyFailed`.

### `ModelVersion` — версия модели

**Ключ:** `model_version_id`.

**Инварианты:** версия неизменяема после публикации; вывод версии из эксплуатации не
удаляет её (нужна для воспроизводимости прошлых заключений); метрики качества
привязаны к версии.

**События:** `ModelVersionPublished`, `ModelVersionRetired`, `ModelDriftDetected`.

## Контекст: Medical Billing

### `ServiceInvoice` — счёт за оказанную услугу

| | |
|---|---|
| **Ключ** | `invoice_id` |
| **Границы** | позиции счёта, тариф, плательщик, состояние, ссылки на источник оплаты |

**Инварианты**

* Сумма счёта = сумма позиций; изменение позиции пересчитывает итог в той же транзакции.
* Оплаченный счёт неизменяем; корректировка оформляется сторнирующим документом.
* Счёт выставляется только на завершённый приём (`EncounterCompleted`).
* Счёт не содержит клинического содержания услуги — только код услуги и тариф.

**События:** `ServiceInvoiceIssued`, `ServiceInvoiceSettled`, `ServiceInvoiceVoided`.

### `InsuranceClaim` — обращение в страховую

**Ключ:** `claim_id`. **Инварианты:** одно обращение относится к одному счёту;
повторная подача создаёт новую версию обращения; отказ страховой не изменяет счёт,
а порождает событие для домена биллинга.

**События:** `InsuranceClaimSubmitted`, `InsuranceClaimAccepted`, `InsuranceClaimRejected`.

## Контекст: Lending

### `LoanApplication` — кредитная заявка

| | |
|---|---|
| **Ключ** | `application_id` |
| **Границы** | параметры запроса, результат скоринга, решение, состояние |

**Инварианты**

* Переход состояний: `submitted → scored → approved | rejected → (agreement_created)`.
  Решение по неоценённой заявке невозможно.
* Одобрение имеет срок действия; по истечении заявка переходит в `expired`.
* У одного `party_id` не может быть двух активных заявок по одному кредитному продукту.
* Решение сохраняет ссылку на версию скоринговой модели и набор факторов — требование
  объяснимости решения перед клиентом и регулятором.

**События:** `LoanApplicationSubmitted`, `LoanApplicationScored`, `LoanApplicationApproved`,
`LoanApplicationRejected`, `LoanApplicationExpired`.

### `CreditAgreement` — кредитный договор

| | |
|---|---|
| **Ключ** | `agreement_id` |
| **Границы** | стороны, сумма, ставка, срок, состояние, ссылка на заявку |

**Инварианты**

* Договор создаётся только из одобренной и не истёкшей заявки.
* Существенные условия (сумма, ставка, срок) после подписания не изменяются —
  изменение оформляется дополнительным соглашением как новой версией.
* Договор не может быть закрыт при ненулевой задолженности.

**События:** `CreditAgreementCreated`, `CreditAgreementAmended`, `CreditAgreementClosed`.

### `RepaymentSchedule` — график платежей

**Ключ:** `schedule_id` (один активный на `agreement_id`).

**Инварианты:** сумма платежей по графику соответствует сумме долга и ставке; активным
может быть только один график; перерасчёт создаёт новую версию, старая сохраняется
для аудита; платёж не может быть отнесён к периоду, которого нет в графике.

**События:** `RepaymentScheduleActivated`, `RepaymentReceived`, `RepaymentOverdue`,
`RepaymentScheduleRecalculated`.

## Контекст: Accounts & Payments

### `Account` — счёт

| | |
|---|---|
| **Ключ** | `account_id` |
| **Границы** | владелец (`party_id`), валюта, состояние, баланс как производная от проводок |

**Инварианты**

* Баланс не пересчитывается «на месте»: он выводится из проводок (`LedgerEntry`),
  что делает историю доказуемой.
* Дебетовая операция не может привести к отрицательному балансу, если у счёта нет
  разрешённого овердрафта.
* Заблокированный счёт не принимает расходные операции.

**События:** `AccountOpened`, `AccountBlocked`, `AccountClosed`.

### `Payment` — платёж

| | |
|---|---|
| **Ключ** | `payment_id`; ключ идемпотентности — `idempotency_key` от инициатора |
| **Границы** | стороны, сумма, назначение, состояние, связанные проводки |

**Инварианты**

* Платёж идемпотентен: повторная команда с тем же `idempotency_key` не создаёт второй перевод.
* Проводки платежа сбалансированы (дебет = кредит) в одной транзакции.
* Отмена проведённого платежа выполняется только сторнированием, физического удаления нет.

**События:** `PaymentInitiated`, `PaymentCaptured`, `PaymentFailed`, `PaymentReversed`,
`FundsDisbursed`.

## Контекст: Workforce

### `Employee`

**Ключ:** `employee_id` (связан с `party_id`).
**Инварианты:** сотрудник не может иметь пересекающихся смен; квалификация имеет срок
действия и по его истечении перестаёт учитываться при назначении на приём; увольнение
закрывает будущие смены в той же транзакции.

**События:** `EmployeeHired`, `EmployeeQualificationUpdated`, `ShiftPlanned`, `EmployeeTerminated`.

## Контекст: Inventory & Equipment

### `StockItem` / `Equipment`

**Ключи:** `sku_id` + `location_id`; `equipment_id`.
**Инварианты:** остаток не может быть отрицательным; списание требует наличия остатка
в конкретной локации; оборудование с просроченным обслуживанием не может быть назначено
на приём (правило, потребляемое доменом Patient Access).

**События:** `StockReceived`, `StockConsumed`, `StockLevelLow`,
`EquipmentMaintenanceDue`, `EquipmentDecommissioned`.

## Контекст: Data Platform

### `DataProduct`

| | |
|---|---|
| **Ключ** | (`domain`, `product_name`, `version`) |
| **Границы** | схема, семантика, SLA, класс конфиденциальности, владелец, происхождение |

**Инварианты**

* Продукт не публикуется без владельца, SLA и класса конфиденциальности.
* Продукт класса PHI не может иметь потребителя в аналитическом контуре — проверка
  выполняется при публикации, а не при чтении.
* Несовместимое изменение схемы порождает новую major-версию; предыдущая версия живёт
  до окончания объявленного окна поддержки.
* Публикация возможна только после прохождения Quality Gate.

**События:** `DataProductPublished`, `DataProductDeprecated`, `DataQualityViolated`.

### `AccessGrant`

**Ключ:** `grant_id`. **Инварианты:** доступ выдаётся на продукт и уровень детализации,
а не «на схему»; срок действия обязателен; отзыв мгновенно влияет на исполнение запросов;
каждая выдача и отзыв журналируются неизменяемо.

**События:** `AccessRequested`, `AccessGranted`, `AccessRevoked`.

## Сводка: почему границы проведены именно так

| Решение | Альтернатива, которую отвергли | Причина |
|---|---|---|
| `Encounter` и `Appointment` — разные агрегаты в разных контекстах | один агрегат «Визит» | у них разные жизненные циклы, разные владельцы и разные требования к конфиденциальности |
| `ProviderSchedule` — агрегат по (врач, день) | агрегат «всё расписание клиники» | конкуренция за слоты решается в одной транзакции, но блокировка не затрагивает всю клинику |
| Баланс `Account` — производная от проводок | хранимое поле «баланс» | доказуемость истории, требование банковского учёта и аудита |
| `LoanApplication` и `CreditAgreement` — разные агрегаты | один агрегат «Кредит» | заявка живёт днями и может не стать договором; договор живёт годами |
| `Party` вынесен в отдельный общий домен | у каждого домена свой клиент | без общего ключа невозможна сквозная аналитика — это текущая боль компании |
| `ConsentGrant` — отдельный агрегат, а не поле пациента | флаг «согласен» в карточке | согласие имеет цель, срок, состав и историю; регулятор требует доказуемости |
