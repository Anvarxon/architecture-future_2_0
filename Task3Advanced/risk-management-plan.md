# План управления рисками

Для каждого риска из [risk-map.md](risk-map.md) указаны: стратегия, конкретные меры,
владелец, измеримый индикатор и план на случай реализации.

Стратегии: **снижение** (уменьшить вероятность или влияние), **избежание** (изменить
решение так, чтобы риск исчез), **передача** (страхование, подрядчик, SLA поставщика),
**принятие** (осознанно принять с мониторингом).

---

## 1. Риски, снижаемые техническими решениями

### A1 — распределённый монолит (🔴)

**Стратегия:** снижение через архитектурные ограничения, проверяемые автоматически.

| Мера | Как реализуется |
|---|---|
| Асинхронность по умолчанию | синхронный вызов между доменами требует явного архитектурного решения (ADR) с обоснованием |
| Фитнес-функция в CI | тест архитектуры считает синхронные межсервисные вызовы на критическом пути; превышение порога роняет сборку |
| Реплики вместо запросов | подписчику нужны данные другого домена — он строит собственное read-модель из событий, а не ходит в чужой API |
| Изоляция отказов | timeouts, circuit breaker, bulkhead на всех оставшихся синхронных вызовах |

**Индикатор:** доля синхронных межсервисных вызовов на критическом пути: базовый уровень
→ −50 % к 18 месяцу → 0 на критическом пути к 36 месяцу (совпадает с целью этапа 3).
**Владелец:** главный архитектор.
**План Б:** если к 18 месяцу показатель не снижается — пересмотр границ доменов
(вероятно, реализовался риск A6), а не добавление новых сервисов.

### A2 — расхождение цифр между доменами (🔴)

**Стратегия:** снижение — сделать расхождение видимым и ограниченным вместо попытки его отрицать.

| Мера | Как реализуется |
|---|---|
| SLA свежести в контракте | каждый дата-продукт объявляет задержку (например, «не более 15 минут»); портал показывает время актуальности рядом с числом |
| Сверочные витрины | автоматическая ежедневная сверка ключевых показателей между доменами; расхождение выше допуска → алерт владельцам, а не пользователю |
| Идемпотентность и exactly-once по бизнес-эффекту | ключ дедупликации в каждом событии, обработчики устойчивы к повтору |
| Единая точка времени | все события несут `occurred_at` домена-источника; агрегация идёт по событийному времени, а не по времени загрузки |

**Индикатор:** расхождение контрольных показателей между доменами ≤ 0,1 % на суточном
горизонте.
**Владелец:** платформенная команда данных + Data Product Owner'ы.

### A4 — утечка PHI (🟠, влияние критическое)

**Стратегия:** избежание — сделать утечку технически невозможной, а не запрещённой регламентом.

| Мера | Как реализуется |
|---|---|
| Классификация в контракте | обязательное поле класса конфиденциальности; продукт без класса не публикуется |
| Запрет коннектора | продукты класса PHI не имеют физического маршрута в lakehouse: политика платформы, а не инструкция |
| Псевдонимизация на выходе домена | вместо идентификатора пациента — токен; обратное сопоставление только внутри медицинского домена |
| Автоматический сканер схем | CI проверяет схемы событий на медицинские поля (диагнозы, коды МКБ, тексты заключений) и блокирует публикацию |
| Аудит и DLP | неизменяемый журнал доступа и выгрузок, контроль экспорта |

**Индикатор:** ноль инцидентов класса PHI; 100 % дата-продуктов имеют класс
конфиденциальности; ежеквартальный аудит подтверждает отсутствие PHI в аналитическом контуре.
**Владелец:** CISO + владелец медицинского домена.

### A5 — отсутствие мастер-данных (🟠)

**Стратегия:** снижение. Выделяется общий домен **Identity & Party** (единый идентификатор
физического лица), публикующий события `PartyIdentified` / `PartyMerged`. Домены
Клиники и Финтех ссылаются на общий `party_id`, сохраняя свои локальные профили.
**Индикатор:** доля сквозных отчётов, собираемых без ручного сопоставления, > 95 %.
**Владелец:** архитектор данных.

### A7 — отказ событийной шины (🟠)

**Стратегия:** снижение техническими средствами + учения.
Мультизональный кластер Kafka (min.insync.replicas ≥ 2), георезервирование для критичных
топиков, изоляция топиков по доменам с квотами, регулярные учения по отказу зоны
(game day) с фиксацией фактического RTO.
**Индикатор:** подтверждённые учениями RTO ≤ 15 мин, RPO = 0 для критичных топиков.
**Владелец:** платформенная команда.

### A8 — ломающие изменения схем (🟡)

**Стратегия:** снижение. Обязательная проверка совместимости в Schema Registry
(BACKWARD), версионирование топиков, окно параллельной публикации старой и новой версии,
контрактные тесты подписчиков в CI издателя.
**Индикатор:** ноль инцидентов из-за несовместимости схем; ≤ 30 % изменений — major.

### T3 — CDC с SQL Server 2008 (🟠)

**Стратегия:** снижение с запасным вариантом.
Основной путь — включение штатного CDC SQL Server на реплике (не на основном сервере),
чтение реплики коннектором. Обязательное нагрузочное тестирование до включения на проде.
**План Б:** если захват изменений недопустим по нагрузке или несовместим — переход на
инкрементальную выгрузку по временным меткам и «мосты» на уровне ESB Camel до момента,
когда домен станет источником истины.
**Индикатор:** прирост нагрузки на промышленную БД от захвата изменений < 10 %.

### T4 — рост стоимости облака (🟠)

**Стратегия:** снижение через FinOps-практики.
Обязательные метки ресурсов (домен, окружение, центр затрат — реализовано в модуле
Terraform из Task 1), бюджеты и алерты на домен, политики жизненного цикла для сырых
слоёв, лимиты на дорогие Trino-запросы, ежемесячный разбор расходов с владельцами доменов.
**Индикатор:** отклонение факта от плана расходов ≤ 10 % в месяц; стоимость на 1 ТБ
обработанных данных снижается квартал к кварталу.
**Владелец:** платформенная команда + финансовый контролёр.

### T5 — недостижение near-real-time SLA (🟡)

**Стратегия:** снижение. Нагрузочное тестирование потоковых витрин на пиковых профилях,
партиционирование топиков с запасом, автомасштабирование Flink, деградация с явным
контрактом: при перегрузке потребитель получает batch-версию витрины с пометкой о задержке.
**Индикатор:** p99 лага потребителя в пределах объявленного SLA в 99 % интервалов.

### T8 — компрометация секретов CI/CD (🟠)

**Стратегия:** снижение (реализовано в Task 2).
Состояние Terraform — только в защищённом хранилище с шифрованием KMS и версионированием;
отдельный сервисный аккаунт на окружение; секреты — только в защищённых переменных CI;
целевое состояние — федеративная идентичность (OIDC) вместо статических ключей;
обязательная ротация ключей; журналирование всех операций apply.
**Индикатор:** ноль секретов в репозитории (проверяется сканером в CI); возраст ключей ≤ 90 дней.

### T9 — деградация legacy DWH под двойной нагрузкой (🟡)

**Стратегия:** снижение. Захват изменений — только с реплики, разведение окон
регламентных отчётов и потоков репликации, мониторинг времени формирования ключевых
отчётов как контрольной метрики.
**Индикатор:** время формирования топ-10 отчётов не растёт более чем на 10 % относительно базовой линии.

## 2. Риски, снижаемые управленческими подходами

### O1 — нет владельцев дата-продуктов (🔴)

**Стратегия:** избежание — без назначенных владельцев этап не стартует.

| Мера | Как реализуется |
|---|---|
| Роль в штатном расписании | Data Product Owner — выделенная роль с KPI, а не нагрузка «сверху» |
| Входной критерий этапа | домен не включается в программу, пока не назначен владелец и не описан первый контракт |
| Публичный каталог | продукт без владельца и SLA не публикуется — правило действует технически |
| KPI владельца | доля потребителей, довольных SLA; количество инцидентов качества; время реакции |

**Индикатор:** 100 % опубликованных продуктов имеют владельца, SLA и контакт для эскалации.
**Владелец:** директор по данным (CDO).

### O2 — дефицит компетенций (🔴)

**Стратегия:** снижение + частичная передача.
Комбинация трёх мер: наём ядра платформенной команды в первые 3 месяца; внешний партнёр
с экспертизой Kafka/Flink на время пилота с обязательной передачей знаний (парная работа,
а не «под ключ»); внутренняя программа обучения — data-инженеры доменов проходят её
на реальном пилоте. Ограничение стека: одна технология на задачу (см. техрадар в Task 5),
чтобы не размывать компетенции.
**Индикатор:** к 12 месяцу ≥ 70 % задач платформы закрываются внутренними инженерами.
**Владелец:** CTO + HR.

### O3 — потеря носителей знаний о DWH (🟠)

**Стратегия:** снижение через фиксацию знаний, пока носители доступны.
Реестр бизнес-правил DWH (что делает процедура, кому принадлежит правило, где
используется) — обязательный артефакт первого этапа; удерживающие соглашения с ключевыми
сотрудниками на период миграции их домена; парная работа «носитель + инженер домена»
при переносе каждого правила.
**Индикатор:** ≥ 90 % бизнес-правил DWH описаны в реестре к концу 12 месяца.
**Владелец:** руководитель программы трансформации.

### O4 — падение приоритета проекта (🟠)

**Стратегия:** снижение через ранние измеримые эффекты.
Пилот выбирается по критерию «быстрый видимый эффект для бизнеса» (финансовые расчёты
или пациентский поток — как и предусмотрено этапом 1). Отчётность перед правлением
ведётся в бизнес-метриках: время формирования отчёта, time-to-market нового отчёта,
доля самостоятельных отчётов. Промежуточные результаты фиксируются каждые 3 месяца.
**Индикатор:** время формирования сложного отчёта — часы → минуты уже на пилоте;
time-to-market нового отчёта — недели → дни.
**Владелец:** спонсор программы со стороны бизнеса.

### O5 — сопротивление пользователей (🟡)

**Стратегия:** снижение. Операторы клиник участвуют в проектировании нового интерфейса;
период параллельной работы со старым PowerBuilder-клиентом; обучение и «чемпионы»
в каждой клинике; переключение по клиникам волнами, а не одномоментно.
**Индикатор:** доля операций в новом UI ≥ 80 % через 3 месяца после запуска волны.

### O6 — конфликт определений метрик (🟠)

**Стратегия:** снижение через федеративное управление.
Совет по управлению данными (представители доменов + CDO) утверждает глобальные метрики;
определения хранятся как код в семантическом слое и проходят ревью; локальные метрики
домена живут в его неймспейсе и не конфликтуют с глобальными.
**Индикатор:** 100 % метрик уровня правления имеют единственное утверждённое определение.

### O7 — регуляторные ограничения (🟠)

**Стратегия:** снижение + передача части ответственности провайдеру.
Юридическая и ИБ-оценка до начала переноса каждого класса данных; аттестованные сегменты
облака для персональных и банковских данных; медицинские данные и данные банка размещаются
в контурах, соответствующих требованиям, с сохранением локализации; для новых регионов —
проверка локальных требований до входа в регион, архитектура допускает региональные контуры.
**Индикатор:** ноль замечаний регулятора; согласование класса данных — до старта переноса, а не после.
**Владелец:** CISO + юридическая служба.

### O8 — размывание ответственности (🟡)

**Стратегия:** снижение. Матрица ответственности RACI на сквозные потоки данных;
дежурство по инцидентам качества с явным первым ответственным (владелец продукта-источника);
единый процесс эскалации с целевым временем реакции.
**Индикатор:** время до назначения ответственного по инциденту качества ≤ 1 час.

### A3 — витрина превращается в новый DWH (🟠)

**Стратегия:** снижение — управленческая мера, поддержанная техническим ограничением.
Платформенная команда работает как поставщик самообслуживания: её KPI — время выпуска
нового дата-продукта силами домена, а не количество построенных ею витрин. Правило:
платформа не пишет доменные трансформации. Домен, не имеющий ресурса, получает временную
поддержку с явной датой передачи ответственности.
**Индикатор:** доля dbt-моделей, принадлежащих доменам, ≥ 80 % к 18 месяцу.

### A6 — неверные границы доменов (🟠)

**Стратегия:** снижение. Границы определяются через Event Storming с участием бизнеса
(см. Task 4), а не по оргструктуре; пересмотр границ — плановая процедура на этапе 2,
а не признак провала; «горячие» контракты (часто меняющиеся) — сигнал к пересмотру границы.
**Индикатор:** доля major-изменений контрактов ≤ 30 % на этапе 1 и ≤ 10 % на этапе 3.

### T1 — миграция сотен терабайт (🔴)

**Стратегия:** снижение через порядок работ (управленческая мера) и инструменты (техническая).
Миграция идёт доменами, а не целиком; сначала — данные, нужные пилоту. Правило «сначала
поток, потом история»: новый контур включается на текущих данных, историческая загрузка
идёт фоном. Обязательная сверка контрольных сумм и количества записей. Данные, не имеющие
потребителя, не мигрируют вовсе — часть объёма просто не переносится.
**Индикатор:** пробная миграция домена укладывается в расчётное окно ±20 %;
100 % перенесённых наборов прошли сверку.
**План Б:** для сверхбольших исторических объёмов — холодное хранение с отложенным
доступом вместо полной миграции в горячий слой.

### T2 — отсутствие паритета отчётности (🔴)

**Стратегия:** избежание — паритет становится входным критерием отключения легаси.
Набор контрольных отчётов согласуется с бизнесом до начала миграции домена;
период параллельной работы двух контуров с автоматической сверкой; допуск расхождения
фиксируется заранее; легаси-отчёт отключается только после N периодов сходимости.
**Индикатор:** 100 % контрольных отчётов сходятся в пределах допуска три отчётных периода подряд.
**Владелец:** владелец домена + финансовый контролёр.

### T6 — недокументированная логика PowerBuilder и хранимых процедур (🟠)

**Стратегия:** снижение. Реверс-инжиниринг с фиксацией в реестре бизнес-правил;
характеризационные тесты (поведение старой системы записывается как эталон до переписывания);
бизнес подтверждает каждое найденное правило — часть из них окажется устаревшей и не будет перенесена.
**Индикатор:** для каждого переносимого процесса есть набор эталонных сценариев.

### T7 — vendor lock-in (🟡)

**Стратегия:** осознанное принятие с ограничением.
Ядро (Kafka, Iceberg, dbt, Trino, Flink) — открытые технологии, переносимые между
облаками; проприетарные управляемые сервисы допускаются там, где стоимость переезда
заведомо ниже выгоды от управляемости. Инфраструктура описана в Terraform (Task 1–2),
что снижает стоимость переезда. Решение фиксируется в ADR с оценкой стоимости выхода.
**Индикатор:** доля проприетарных сервисов на критическом пути ≤ 20 %.

## 3. Сводка: что решается техникой, а что управлением

| Только техническими решениями | Только управленческими решениями | Требует и того, и другого |
|---|---|---|
| A7 (отказоустойчивость шины) | O1 (владельцы дата-продуктов) | A1 (архитектурные правила + фитнес-функции в CI) |
| A8 (совместимость схем) | O2 (компетенции: найм, обучение, партнёр) | A2 (сверки + SLA, согласованные с бизнесом) |
| T5 (производительность потоков) | O3 (удержание знаний и людей) | A3 (KPI платформы + запрет доменных трансформаций) |
| T8 (защита секретов и состояния) | O4 (приоритет и спонсорство) | A4 (техническая блокировка + аудит комплаенса) |
| T9 (разведение нагрузки) | O5 (управление изменениями) | A5, A6 (моделирование доменов с бизнесом) |
| | O6 (совет по данным), O8 (RACI) | T1, T2, T3, T4, T6, T7 |

**Наблюдение.** Из шести критических рисков только два (T1, T2) — преимущественно
технические. Остальные четыре (A1, A2, O1, O2) реализуются или не реализуются в
зависимости от организационных решений: кто владеет данными, как устроены KPI команд и
насколько бизнес участвует в определении границ доменов. Программа трансформации
«Будущего 2.0» — в первую очередь организационная, и технический план должен это учитывать.
