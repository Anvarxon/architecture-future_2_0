# Расширенный технологический радар «Будущее 2.0»

Радар включает не только технологии, но и **архитектурные паттерны и практики** —
именно они определяют результат трансформации в большей степени, чем выбор конкретного
продукта.

## Кольца

| Кольцо | Значение для компании |
|---|---|
| **Adopt** | стандарт по умолчанию; отклонение требует обоснования в ADR |
| **Trial** | применяем в пилотах и на ограниченном контуре, готовы масштабировать при подтверждении |
| **Assess** | изучаем, делаем прототипы, решение не принято |
| **Hold** | не начинаем новых работ; существующее использование планомерно сворачиваем |

Машиночитаемая версия — [tech-radar.csv](tech-radar.csv) (формат, совместимый с
[ThoughtWorks Build Your Own Radar](https://radar.thoughtworks.com/)).

## Квадрант 1. Архитектурные паттерны и практики

### Adopt

| Позиция | Почему |
|---|---|
| **Event-Driven Architecture** | целевой способ взаимодействия доменов; снимает временну́ю связанность, дающую сегодня каскадные отказы |
| **Domain-Driven Design / Bounded Contexts** | язык и границы доменов — основа независимого развития направлений |
| **Data Mesh (доменное владение данными)** | прямой ответ на требование «развивать каждое направление отдельно, сохраняя целостное представление» |
| **Data Contracts** | контракт как код: схема + семантика + SLA + класс конфиденциальности; проверяется в CI |
| **Self-service BI** | цель № 1 бизнеса: сотрудник строит отчёт сам в пределах своего доступа |
| **Infrastructure as Code** | все среды из Terraform-модулей (Task 1–2); ручные изменения инфраструктуры запрещены |
| **Change Data Capture** | способ включить легаси-DWH в событийный контур без переписывания |
| **Transactional Outbox** | гарантия «изменение и событие — атомарно» без распределённых транзакций |
| **Anti-Corruption Layer** | не даёт модели SQL Server протечь в новые домены |
| **Strangler Fig** | безопасный вывод легаси: функция за функцией, с тестом на паритет |
| **Schema-first + реестр схем** | обратная совместимость проверяется до релиза, а не инцидентом на проде |
| **ABAC / RLS + маскирование** | доступ по атрибутам сотрудника; предикаты подставляются до исполнения запроса |
| **Псевдонимизация PHI на границе домена** | техническая гарантия того, что медданные не попадут в аналитику |
| **Medallion-архитектура (bronze/silver/gold)** | понятная всем доменам структура слоёв дата-продукта |
| **FinOps: обязательная разметка ресурсов** | без меток «домен/окружение/центр затрат» расходы облака неуправляемы (риск T4) |

### Trial

| Позиция | Где пробуем |
|---|---|
| **CQRS** | домены с сильно различающимися профилями чтения и записи: Patient Access, Accounts |
| **Event Sourcing (точечно)** | агрегаты, где важна история: `CreditAgreement`, `ConsentGrant`, `LedgerEntry` |
| **Streaming data products** | пилотные near-real-time витрины (поток пациентов, платежи) |
| **Semantic layer as code** | определения метрик в Git с ревью — лекарство от риска O6 (разные определения выручки) |
| **Policy as Code (OPA)** | правила доступа и правила платформы («в prod нет прерываемых ВМ») вне кода приложений |
| **Contract testing** | тесты подписчиков в конвейере издателя |
| **Fitness functions в CI** | автоматический контроль архитектурных ограничений — противоядие риску A1 |
| **Data product SLO** | свежесть и полнота как обязательство владельца, а не пожелание |
| **Game days / учения по отказам** | проверка реального RTO событийной магистрали |
| **Feature Store** | переиспользование признаков между ИИ-сервисами внутри медицинского контура |

### Assess

| Позиция | Что выясняем |
|---|---|
| **Федеративное обучение и синтетические данные** | можно ли обучать модели без выноса PHI за пределы клиники — важно при выходе в новые регионы |
| **Differential privacy для агрегатов** | допустимо ли публиковать тонкие медицинские срезы без риска реидентификации |
| **Zero-copy data sharing** | обмен дата-продуктами с партнёрами (фарма, страховые) без копирования |
| **Reverse ETL** | возврат аналитических признаков в операционные системы |
| **LLM-ассистент витрины (text-to-SQL поверх семантического слоя)** | снижение порога входа для бизнес-пользователя; критично соблюдение прав доступа |
| **Active metadata / автоматический lineage** | построение происхождения данных без ручного описания |
| **Монетизация дата-продуктов и ИИ-функций** | внешние потребители как источник выручки (цель третьего года) |

### Hold

| Позиция | Почему сворачиваем |
|---|---|
| **Бизнес-логика в хранимых процедурах DWH** | корневая причина медленного time-to-market; переносится в домены |
| **Общая база как способ интеграции** | схема, которую читают все, не может изменяться — источник связанности |
| **ETL-логика внутри шины (Camel-маршруты)** | третье место, где живёт бизнес-логика |
| **Точечные синхронные интеграции на критическом пути** | каскадные отказы; отключаются на этапе 3 |
| **Кастомизации BI поверх сырых таблиц DWH** | каждое новое направление требует правки центральной модели |
| **Единая универсальная модель данных на всю компанию** | попытка описать все домены одной схемой уже реализована в текущем DWH и не масштабируется |
| **Ручные выгрузки в Excel как способ отчётности** | неуправляемый и неаудируемый канал распространения данных |

## Квадрант 2. Платформы

### Adopt

| Позиция | Роль |
|---|---|
| **Облачная платформа РФ (Yandex Cloud)** | целевая среда; управляемые сервисы вместо собственного железа |
| **Управляемый Apache Kafka** | событийная магистраль |
| **Object Storage (S3-совместимый)** | хранение lakehouse и состояния Terraform |
| **Apache Iceberg** | табличный формат lakehouse: версионность, эволюция схемы, time travel |
| **Kubernetes** | среда исполнения доменных сервисов |
| **PostgreSQL** | операционные БД доменов |
| **Keycloak / корпоративный IdP** | единая идентификация, источник атрибутов для ABAC |

### Trial

| Позиция | Что проверяем |
|---|---|
| **Trino** | федеративный SQL-доступ без копирования данных |
| **Apache Flink** | потоковые витрины и near-real-time агрегация |
| **ClickHouse** | оперативные витрины с субсекундным откликом |
| **DataHub / OpenMetadata** | каталог дата-продуктов и происхождение данных |
| **MLflow** | реестр моделей и воспроизводимость заключений ИИ |
| **Power BI поверх семантического слоя** | сохранение привычного инструмента без кастомизаций поверх DWH |

### Assess

| Позиция | Что выясняем |
|---|---|
| **Iceberg REST Catalog** | единый каталог таблиц для нескольких движков |
| **Kafka Tiered Storage** | удешевление длительного хранения лога событий |
| **Геораспределённое развёртывание (2–3 региона)** | требования локализации данных в новых регионах |
| **Векторная БД** | поиск по медицинским документам внутри защищённого контура |
| **Serverless-обработка данных** | экономика нерегулярных нагрузок |

### Hold

| Позиция | Почему |
|---|---|
| **Microsoft SQL Server 2008 (DWH)** | вне поддержки, уязвимости не устраняются, комплаенс-риск; вывод к 36 месяцу |
| **Собственное оборудование в ЦОД** | стоимость поддержки устаревшего парка при переезде в облако |
| **Apache Camel как целевая шина интеграций** | остаётся только мостом совместимости с датой вывода |
| **Power BI Premium как единственная точка отчётности** | не даёт самообслуживания при росте числа доменов |

`Ручные скрипты миграции данных без версионирования` · `Секреты в конфигурационных файлах`

## Как радар связан с этапами трансформации

| Этап | Что переходит в Adopt | Что переходит в Hold |
|---|---|---|
| **1 (0–6 мес)** | EDA, DDD, Data Contracts, IaC, CDC, Outbox, Schema Registry | локальное состояние Terraform, новые доработки бизнес-логики в DWH |
| **2 (6–18 мес)** | Trino, Flink, каталог дата-продуктов, Policy as Code, Data Mesh на критических доменах | ETL-логика в Camel, кастомизации BI поверх DWH |
| **3 (18–36 мес)** | streaming data products, semantic layer as code, near-real-time витрины | SQL Server 2008, Camel как интеграционный слой, синхронные интеграции на критическом пути |

Радар пересматривается **раз в квартал** архитектурным комитетом. Перемещение позиции
между кольцами оформляется ADR с обоснованием — это защищает от ситуации, когда
технология оказывается в Adopt «потому что её уже кто-то внедрил».
